进一步按原始响应字段核查：共有 8 组重复 response ID，涉及 59 次调用。8 组中同 ID 的 `choices` 与 `usage` 均逐字段相同，却都有不同的 `created` 时间和不同的 HTTP provider request ID。因此这**不是原始 JSON 字节级复用**，更准确地说是“响应 ID、选择结果及用量复用，响应信封部分字段重新生成”。这个事实仍不足以区分后端缓存、确定性生成或代理层重组；尤其不能把 `created` 时间不同当作 59 次独立模型推理的证明。

## 研究解释与后续判别

retail 查找锚点从 Pilot 的 1/8 到本块的 24/24，是明确的**调用层面表观变化**；但去重后只有 Pilot 1/6 与本块 2/2，绝不能用 24 次独立 Bernoulli 试验计算显著性。Pilot 最后一次请求约 03:06 UTC，本块约 07:45 UTC；该对比涉及数小时的服务条件差异，也可能是随机结果与响应复用共同作用，尚不能声称模型漂移。

**对另一 retail 锚点的内容级修正：**先前将原轨迹的 `COMMUNICATE` 与重复样本的 `ACT:calculate` 称为“相反结果”，这仅在下一步粗动作层面成立。冻结请求末尾已有一次 `calculate({"expression":"196.73 - 197.33"})`，得到头盔差价 -0.60；原轨迹随后在用户回复中直接写出行李差价 -43.59、烤炉差价 -94.55，并请求用户确认。Pilot 的 8/8 与时间块 0 的 24/24 次重复响应，调用的却都是新的 `calculate({"expression":"452.28 - 495.87"})`，即计算**行李**差价 -43.59，并非重复算头盔。故更合适的研究标签是“调用工具核算后再回复”与“直接给出已算差价并请求确认”的下一步策略分歧；它不证明任务意图或最终结果相反。由于 Agent-only 不执行该工具，也无法确定重复路线后续会如何向用户确认。

后两块维持原冻结计划与硬预算，不提前采样。每块结束后应并列报告：调用次数、不同 response ID、不同动作签名、动作类别比例、各锚点的采样跨度，以及跨块 response ID 是否重现。只有跨时段且在去重视角下仍可见的变化，才值得进一步讨论“运行条件变化”；即便如此，Agent-only 设计仍不能给出工具执行或闭环成功率结论。

## 补充：粗“交流”标签掩盖的用户可见行为
